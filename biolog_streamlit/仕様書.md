# BioLog 仕様書（v1.5.5 時点）

## 1. 設計原理

### 1.1 単一 Writer モデル
書き込みは API + Worker(1スレッド) に集約し、SQLite ロック競合を構造的に回避する。
```
Streamlit → POST/PUT/DELETE → FastAPI → Queue → Worker(1スレッド) → db_manager → SQLite
```
- フロント（Streamlit）は読み取り中心、書き込みは API 経由のみ
- DB の正しさはバックエンド責務（フロントで整合性担保しない）

### 1.2 「1日 1 点」ルール（データ仕様）
- `health_records` テーブルに UNIQUE INDEX `(user_id, date)` を持つ
- 同一 user + 同一日付の登録は worker.py の `ON CONFLICT(user_id, date) DO UPDATE` で UPSERT
- グラフ描画でも 1 日 1 点に集約してから可視化（`groupby(["user_id","date"]).last()`）

### 1.3 Eventual Consistency 許容
- 登録 → DB 反映 → 表示まで数秒のラグを許容
- UX 上の文言で期待値調整：「登録を受け付けました（反映には数秒かかる場合があります）」
- 「更新」ボタンで明示 invalidate 可能

## 2. データフロー

### 2.1 登録（POST / PUT / DELETE）
```
Streamlit form → api_post/put/delete → FastAPI endpoint
              → preprocess.preprocess_record（型補正・date 補完）
              → Pydantic 検証（HealthRecordCreate/Update）
              → _enqueue_and_wait → Worker（INSERT/UPSERT/UPDATE/DELETE）
              → 結果を result_queue で API スレッドに返却
              → API レスポンス返却
```

### 2.2 取得（GET）
```
Streamlit → api_get → FastAPI endpoint → biocore.get_*（明示列 SELECT）
         → 結果 JSON 返却
```
GET は biocore.py 経由で SELECT のみ（FastAPI エンドポイント内で直接 sqlite3 を触らない）。

### 2.3 JST 化
- **API 側**：`biolog_api/time_utils.py` の `jst_date()` で `preprocess.py` が date を補完
- **UI 側**：`biolog_streamlit/time_utils.py` の `to_jst()` で `created_at` を JST 表示に変換
- Docker コンテナ TZ は UTC でも JST 基準で date が確定する

## 3. グラフ仕様

### 3.1 描画
- matplotlib + japanize_matplotlib（日本語フォント自動適用）
- `dark_background` スタイルで Streamlit ダークモードと統一
- `st.pyplot(fig, clear_figure=True)` で再描画時の重複防止

### 3.2 X 軸（日付）
- datetime64 のまま matplotlib に渡す
- 表示形式 `mdates.DateFormatter("%m-%d")`
- ティックはデータに実在する日付のみ：`ax.set_xticks(sorted(df["date"].unique()))`

### 3.3 重複防止 3 層
| 問題 | 解決層 |
|---|---|
| 日付重複 | groupby (`user_id`,`date`).last() |
| ラベル重複 | set_xticks(data.unique()) |
| 描画重複 | st.pyplot(clear_figure=True) |

### 3.4 配色
- self: 青 `#1f77b4`
- father: 緑 `#2ca02c`
- mother: 赤 `#d62728`

血圧グラフは収縮期 120 / 拡張期 80 の参考線を `axhline` で表示。

## 4. キャッシュ設計（v1.5.5 以降の現行構成）

### 4.1 キャッシュ宣言
```python
@st.cache_data
def fetch_latest(uid: str):
    return api_get(f"/api/health/records/latest/{uid}", suppress_404=True)

@st.cache_data
def fetch_range_data(start: str, end: str):
    return api_get("/api/health/records/range", params={"start": start, "end": end})
```
- `version` 引数は持たない（v1.5.5 で廃止）
- TTL も指定しない（明示 invalidate で十分）

### 4.2 invalidate ルール
書き込み成功時に **per-function クリア** を必ず呼ぶ：
```python
fetch_latest.clear()
fetch_range_data.clear()
st.rerun()
```

適用箇所：
- サイドバー「更新」ボタン
- 新規登録成功時
- 編集成功時
- 削除成功時

### 4.3 旧 version 機構の廃止理由
- 旧設計：`session_state.latest_version` を `int` で持ち、書き込み時に `+= 1` で cache key を進める
- 問題：新セッションで `latest_version=0` に **リセット** され、過去セッションのキャッシュキー `(uid, 0)` に **衝突** → 古い値が再表示される
- 解決：version を廃止し、明示 invalidate に統一 → セッション跨ぎ問題が構造的に発生しない

## 5. 整合性モデル

### 5.1 採用モデル
**Eventual Consistency（最終的整合性）**

| フェーズ | 状態 |
|---|---|
| API 成功直後 | DB 未反映の可能性あり（Queue 経由のため） |
| 初回表示 | 直近書き込みが見えない可能性あり |
| 数秒後 | 自然整合 |
| 「更新」ボタン | 強制 invalidate |

### 5.2 UX による補正
- 「登録を受け付けました（反映には数秒かかる場合があります）」
- 「※ データは非同期で反映されます。表示が更新されない場合は『更新』を押してください。」

## 6. PII / ログ

### 6.1 マスク対象
`biolog_api/log_utils.py` の `mask_pii(text)` が以下を `****` / `***@***` に置換：
- `"user_id": "..."` / `user_id=...`
- `"request_id": "..."` / `request_id=...`
- 標準 UUID（8-4-4-4-12 形式）
- 32 文字 hex（ハイフン無し UUID 圧縮形）
- email アドレス

### 6.2 マスク非対象
- 健康数値（temperature / weight / pulse / blood_pressure / body_fat / muscle_mass / bmr 等）
- 日付・件数・event 名・status 等
- meal_detail / activity_log の内容

### 6.3 適用箇所
- `api.py` POST 内 local `log()` の print
- `worker.py` `_log()` の print
- update / delete の直接 print はスコープ外（v1.5.4 では非適用）

## 7. migration 機構

### 7.1 runner
`biolog_api/migrations/runner.py`:
- `schema_migrations` テーブルで適用済み migration を管理
- `migration_lock` テーブルで並行実行防止
- 各 migration の `run(conn)` を BEGIN IMMEDIATE 配下で実行 → 成功時に `schema_migrations` に記録
- 失敗時は rollback、再実行で同じ migration がリトライ

### 7.2 migrate_001（CREATE + ALTER 併存構造）
```python
_DDL_CREATE = [
    "CREATE TABLE IF NOT EXISTS health_records (...)",
]
_DDL_MIGRATE = [
    "ALTER TABLE health_records ADD COLUMN request_id   TEXT",
    "ALTER TABLE health_records ADD COLUMN meal_detail  TEXT",
    "ALTER TABLE health_records ADD COLUMN activity_log TEXT",
]
_DDL_INDEXES = [
    "CREATE INDEX IF NOT EXISTS idx_hr_user_date ON health_records(user_id, date DESC)",
    "CREATE UNIQUE INDEX IF NOT EXISTS uidx_hr_user_date ON health_records(user_id, date)",
]
```
- **CREATE と ALTER は環境差吸収のため両方残す**（削除・統合禁止）
- 既存 DB では ALTER が適用済み履歴あり、新規 DB では CREATE のみが意味を持つ
- duplicate column name エラーは silent に吸収

### 7.3 health_records スキーマ（16 カラム）
| カラム | 型 | 制約 |
|---|---|---|
| id | INTEGER | PRIMARY KEY AUTOINCREMENT |
| request_id | TEXT | NOT NULL UNIQUE |
| date | TEXT | NOT NULL |
| user_id | TEXT | NOT NULL |
| temperature | REAL | |
| pulse | INTEGER | |
| systolic_bp | INTEGER | |
| diastolic_bp | INTEGER | |
| weight | REAL | |
| body_fat | REAL | |
| muscle_mass | REAL | |
| bmr | INTEGER | |
| meal_detail | TEXT | |
| activity_log | TEXT | |
| memo | TEXT | NOT NULL DEFAULT '' |
| created_at | TEXT | NOT NULL DEFAULT (datetime('now','localtime')) |

CHECK 制約は省略（既存 DB との互換性最優先、Pydantic 層で範囲検証）。

## 8. Docker 起動制御

### 8.1 entrypoint.sh
```sh
#!/bin/sh
set -e

echo "[entrypoint] running migrations..."
python migrations/runner.py
echo "[entrypoint] migrations complete, starting API..."

exec uvicorn api:app --host 0.0.0.0 --port 8766
```

### 8.2 起動フロー
1. `docker compose up` → コンテナ起動
2. `entrypoint.sh` 実行 → migration runner 起動
3. runner 成功 → uvicorn 起動（PID 1 を引き継ぎ、SIGTERM 正常伝搬）
4. runner 失敗 → `set -e` で exit 1 → restart policy で再起動

### 8.3 docker-compose
- `restart: unless-stopped`
- volume mount: `D:\AI\biolog_streamlit\data:/data`
- environment: `DATABASE_PATH=/data/biolog.db`

## 9. 既知の制約と弱点

### 9.1 個人/家族用前提
- マルチユーザー（不特定多数）想定ではない
- 認証なし。ブラウザのクロスオリジンAPI利用は許可しない

### 9.2 migration_lock 残存
- SIGKILL / コンテナ強制停止で finally が走らない場合、lock 残存
- 復旧：`DELETE FROM migration_lock WHERE id = 1` を手動実行
- runner.py の lock 競合時挙動は exit 0（schema 未整備で API が起動する可能性あり）

### 9.3 SQLite + Windows NTFS バインドマウント
- WAL モード禁止（I/O エラーになる）
- 必ず `PRAGMA journal_mode=DELETE`
- `.db-shm` / `.db-wal` 残骸がないか定期確認

### 9.4 cache 内同セッション内の編集後挙動
- v1.5.5 で per-function `.clear()` 化により基本的に解決
- ただし `updated_at` カラム未実装のため、created_at をキーにした追加最適化は将来検討

### 9.5 2026-07-27 監査対応

- Workerはタスク単位で例外を隔離する。`Exception`はエラー結果へ変換するが、
  `KeyboardInterrupt`と`SystemExit`は捕捉しない。
- Workerのエラー結果は`error_kind`で`not_found`、`validation`、
  `database`、`internal`を区別する。APIはそれぞれ404、422、500へ対応させる。
- Queue応答待ちの`queue.Empty`は503とする。待機時間30秒は変更しない。
- health endpointはWorker生存、DB読取疎通、Queueサイズを検査する。
  healthcheckは監視用であり、Composeの`restart: unless-stopped`による
  自動復旧のトリガーにはならない。
- 一覧は既存の期間取得APIを使用し、選択ユーザーをクライアント側で絞り込む。
  表示は20件ページング、CSVは指定ユーザー・指定期間の全件とする。
- SQLiteは`journal_mode=DELETE`を維持する。接続待機と読取リトライの合計は
  10秒の表示更新周期を超えないよう制限する。
- APIの`limit`は1～500、`offset`は0～10000とする。
  日付は実在する`YYYY-MM-DD`で、期間開始日は終了日以前とする。
- `preprocess.py`の`int(float(v))`による既存入力補正は互換性維持のため変更しない。
- コンテナのTZはComposeで`Asia/Tokyo`へ統一し、コード側で二重補正しない。
- `created_at`はphase 7aのTZ統一境界により、`id <= 146`をUTC保存、
  `id >= 147`をJST保存として表示する。DBを移行するまではこの境界を維持する。
- コンテナプロセスはUID/GID `10001`で実行し、Linux capabilityはすべて破棄する。
  D側反映時は`/data`バインドマウントへの書き込みを確認する。
- Pythonの推移依存版は各サービスの`constraints.txt`に固定する。
  固定値の根拠は2026-07-27時点の動作中イメージの`pip freeze`とする。
- Network issueの原因は未確定とし、`st.fragment`、`st.tabs`、
  Streamlitバージョンを証拠なしに変更しない。

### 9.6 2026-08-01 PyArrow SIGSEGV回避実験

- `docker events`で終了コード`139`、faulthandlerで`st.dataframe`から
  PyArrow列変換中に至るSIGSEGVスタックを取得した。
- 一覧と削除確認ではStreamlitのArrow表ウィジェットを使用せず、列名とセル値を
  エスケープする共通HTMLレンダラーを使用する。欠損値は空欄で表示する。
- 一覧の`st.fragment(run_every="10s")`、ページ送り、CSV、長文の全文表示は維持する。
  HTML表では対話的な列ソートとセル選択は提供しない。
- `PYTHONFAULTHANDLER=1`と終了イベント監視を維持し、反映後7日間は
  再起動・画面初期化回数・一覧とCSVの表示内容を確認する。
- 再発ゼロは症状消失の確認とし、根本原因の確定とは扱わない。安定性とは別に、
  ソート操作の必要性を評価し、必要ならソート列・昇降順の選択機能を追加する。
- Arrow表変換経路を除去した状態で再発した場合は、先行するメモリ破壊または
  別のネイティブ要因を調査し、退避済み旧イメージへロールバックする。

## 10. 絶対に破ってはいけないルール

1. **書き込み経路は 1 本のみ**: `FastAPI → Queue → Worker(1スレッド) → db_manager → SQLite`
2. **`sqlite3.connect()` は `db_manager.py` 以外で呼ばない**（migration runner は例外として隔離 DB 接続 OK）
3. **`PRAGMA journal_mode=WAL` 禁止**（必ず DELETE）
4. **Worker は daemon スレッド 1 本のみ**（`threading.Thread(daemon=True)`）
5. **Queue は `queue_manager.get_queue()` で取得する global singleton 1 個のみ**
6. **FastAPI エンドポイント内で DB を直接操作しない**（GET は biocore 経由で SELECT のみ許可）
7. **Streamlit から DB に直接アクセスしない**（FastAPI への HTTP リクエストのみ）
8. **`lifespan` 内に migration / cleanup を書かない**（migration runner で entrypoint 経由で実行）
9. **`@st.cache_data` 関数は per-function `.clear()` で invalidate する**（session_state version 機構は使わない）
10. **Composeの`TZ=Asia/Tokyo`を外さない**（`created_at`の保存時刻仕様が無警告で変わるため）
