動機

家族（自分 / 父 / 母）の
体温・血圧・脈拍・体重・食事ログ・行動ログを
日次で記録・可視化したい。

必要なもの:

  • ローカル完結（外部サーバにデータ送信しない）
  • Docker 1 コマンドで起動
  • SQLite 単一ファイルで完結
  • スマホからもアクセス可（LAN 内）

構成

設計原則

守るべき制約

  • 書き込みは Worker 1 本
  • sqlite3.connect() は db_manager のみ
  • PRAGMA journal_mode=WAL 禁止
  • FastAPI 内で DB 直接操作禁止
  • Streamlit から DB 直接アクセス禁止

なぜ SQLite?

  • ファイル 1 つ。バックアップは cp
  • 別 DB サーバ不要
  • 家族規模なら年間数千件
  • Windows NTFS で WAL は I/O エラー → DELETE モード強制

Phase 1 — 起動ブロッカー修正

監査で発覚：Streamlit が SyntaxError で起動不能

def is_truncated(full: str, limit: int) -> bool:
    return len(full) > limit
    except Exception as e:   # ← orphan!
        st.error(f"API エラー: {e}")
        return None

原因：以前のリファクタで api_get() の 2 段 except 構造の片方が孤立したまま残った

教訓：「動いている」と「壊れていない」は別物。静的解析と実機検証は両輪。

Phase 2 — DB スキーマ補完

migration ファイルに CREATE TABLE 自体が無かった（ALTER のみ）

新規環境では「テーブル不在」で API 起動失敗。

採用した解：CREATE と ALTER の併存構造

CREATE TABLE と ALTER TABLE は 冗長ではなく
環境差吸収のための 必須構造。
削除・統合は禁止。
  • 既存 DB ← ALTER のみが意味を持つ
  • 新規 DB ← CREATE のみが意味を持つ
  • 両方残すことで両環境を 1 ファイルでカバー

Phase 3 — entrypoint.sh で migration 自動化

#!/bin/sh
set -e

echo "[entrypoint] running migrations..."
python migrations/runner.py
echo "[entrypoint] migrations complete, starting API..."

exec uvicorn api:app --host 0.0.0.0 --port 8766
  • set -e + 直列実行で migration 失敗時は API 起動を阻止
  • exec uvicorn で PID 1 を引き継ぎ SIGTERM 正常伝搬
  • 「手動 migration 忘れ」を構造的に排除

Phase 4 — API ログの PII マスク

監査で発覚：docker logs biolog-api に user_id / request_id / UUID / email が平文出力

def mask_pii(text: str) -> str:
    if text is None:
        return ""
    text = str(text)
    for pattern, repl in _PATTERNS:
        text = pattern.sub(repl, text)
    return text

たった 1 行追加で全ログにマスクが効く設計：

print(mask_pii(json.dumps(entry, ensure_ascii=False)), flush=True)

Cache invalidation の試行錯誤

バージョン方式問題
v1.3.8version 引数 + session_state（init=0）翌日跨ぎで (uid, 0) 衝突 → 前日値
v1.5.5fetch_*.clear() + rerunEC ラグで stale 取得
v1.5.7version 引数（init=int(time.time())）翌日跨ぎ衝突を構造的に回避

「失敗 → 別解 → 旧解の修正版」のループ。Claude との対話で 毎回設計上の差分を言語化 したのが効いた。

Cache invalidation 確定形 (v1.5.7)

if "data_version" not in st.session_state:
    st.session_state.data_version = int(time.time())

@st.cache_data
def fetch_latest(uid: str, version: int):
    # version is intentionally unused for cache invalidation
    return api_get(f"/api/health/records/latest/{uid}", ...)

# 書き込み成功時
st.session_state.data_version += 1
st.rerun()
  • init を int(time.time()) → 翌日跨ぎ衝突を構造的に排除
  • fetch_*.clear() は使わない（version 更新で代替）
  • clear_on_submit=True で form 自動リセット

公開準備 — OSS としての作法

取り組んだこと

  • 個人パスの完全除去
  • .env 化（hardcode 撤廃）
  • LICENSE (MIT) + 免責事項
  • README に 「Not For」 章
  • Known Issues / Untested 明示
  • .gitattributes で改行コード固定

方針

  • 問題を隠さない
  • 未検証範囲を明示する
  • LAN 内専用と明記する
  • SQLite の前提を正直に書く

失敗 ① — データ消失 × 2

公開準備中、AI（私）が破壊的操作を 2 度実行：

  1. docker-compose.yml の volume パス変更
    env 化と同時にデフォルト値変更 → container が新しい空ディレクトリをマウント
  2. 動作中の .env を削除
    「.gitignore で守られているのに念のため削除」という過剰判断

どちらもバックアップで救出 🙇

教訓：.gitignore で守られているなら物理削除は不要。破壊的操作は事前確認が絶対。

失敗 ② — ドキュメント漏れ

公開後にユーザーが気付いた：

「食事ログや行動ログの情報が全体的に抜けてます」

コード側（worker / biocore / schemas / migrate / UI）は完全対応。
しかし API リファレンス skills.md だけ取り残されていた。

教訓：「コード = 仕様」ではない。OSS では ドキュメントも一次成果物。

Claude との協業

Plan Mode を徹底活用

  • 実装前に必ず方針を プランファイル に書き出す
  • 採用方針・触らないもの・触るもの・検証手順を明示
  • 「禁止事項」が地味に効く（暴走防止）

反復改善のリズム

  • plan → reject → 修正版 → reject → … → approve
  • 1 イテレーション当たりの差分は小さい
  • 毎回 なぜ前案がダメか を言語化

AI と作るときに効いたこと

  • 「動かす AI」ではなく「議論する AI」として使う
  • 毎回 「なぜそうするのか」 を AI に説明させる
  • AI の判断ミスは こちらが気付いて止める（過剰判断・推測ベース）
  • 破壊的操作は必ず人間が確認（特に DB / .env / volume）
  • 監査・テスト・公開準備など 「機械的だが知識量必要」 な作業に強い

AI ペアプロは「副操縦士」。判断責任は人間側に残る。
